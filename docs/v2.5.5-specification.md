# ScreenLingo 2.5.5 (build 123): the text blocks of one subtitle are translated together, as built

Base: `claude/screenlingo-v2.5.4`. Work branch: `claude/screenlingo-v2.5.5`. Draft PR into the base branch.
**Nothing was compiled or run in chat** (no Swift compiler). All `scripts/test_*.py` were run. The GitHub Actions run is the first real test.
**The effect on wording is UNVERIFIED.** The report has no subtitle text, so this change was found by reading code and the owner's screenshots, not by a measurement.

## 1. Report and evidence
- Owner report (2.5.4 build 122): sentence structure is broken, "almost always", more often than before; the same sentence is translated and shown several times.
- Report b122 (metadata only): 267 captions in 4.7 min; 121 of 256 gaps between shown captions under 450 ms, in runs of up to 7; about 45% of captions confirm within one OCR read. This fits a subtitle that grows being shown at each step (not changed here) and says nothing about wording.
- Owner screenshots of the source video (Portuguese): a speaker name above the sentence ("Percy:"), bracketed text in two pieces with a large gap between the lines, bracketed text in different colours and places, a two-line sentence.

## 2. What the code does (read, not run)
- `OCRGrouping.makeBlocks` joins lines into one block only when they are stacked closely (edge gap under 0.75 line heights, similar size). Lines further apart are separate blocks.
- `selectBlocks` keeps the blocks of one group (by position) and returns them as separate blocks. `process` translates each block separately (`for (bi, raw) in blocks`), without the others as context. Inside a block, `splitSentences` + `TranslationUnitPlanning.units` split at sentence ends; ellipses are not boundaries and fragments are merged. That part was read and is NOT the cause (an earlier suspicion in chat was wrong).
- A label block such as `Percy:` alone is not recognised by `TextIntel.splitDialogue` (it needs a space after the colon), so it is translated as text.

## 3. Change
`CaptionJoin.joined` (`Shared/TranslationSystem+V255.swift`, pure, no layout rule): when the capture step kept several blocks for the active subtitle, they are joined in reading order into one text (space between words; none for CJK or after a trailing hyphen); more than 240 characters stays as separate blocks. `captionJoinedTexts` (`TranslatorEngine+CaptionJoin.swift`) applies it in `handleContent` right after `extractTexts` (which is unchanged and still equals the e94542ce original), Legacy only. Switch "Translate a subtitle's text blocks together" (`captionJoin`, report arm `captionJoinAB`), default ON, pinned per session with the other switches. OFF gives the 2.5.4 behaviour.
Counters (whole session, confirmed readings): `captionMultiBlock`, `captionJoined`; report table "Text blocks per confirmed reading (2.5.5)".

## 4. Risks
- Changes what is sent to the translator for subtitles with several blocks; wording can differ from 2.5.4 (intended).
- Two unrelated nearby texts of the chosen group are joined into one text and shown as one paragraph (line breaks between blocks are lost).
- Speaker labels now reach `splitDialogue` joined to their sentence; if the label detection is wrong for a language the name is translated.

## 5. Not changed (open)
- A subtitle that grows or fades in is still translated and shown at each step. Needs a text-growth rule (same text with a longer ending) and a decision on the latency it costs; the new counters do not measure it yet.
- Group choice between several text areas on one screen (`movieTextFocus`) was not read in detail.

## 6. Tests
`scripts/test_three_modes.py` 2.5.5 block and the pin-loop assertion; version asserts in eight scripts (2.5.5/123); `Tests/HotPathAB/main.swift` (switch default and off-alone, `CaptionJoin` cases, checked by a Python port in chat, not by Swift).

## 7. Device test

Compare the same captions by eye (structure, repeated sentences) and in the report: readings with several text blocks, how many were joined, latency (a join changes only the text, not the number of reads).
