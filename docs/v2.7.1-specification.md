# ScreenLingo 2.7.1 (build 132): iPad freeze fix

Branch `claude/screenlingo-v2.7.1` from `claude/screenlingo-v2.7.0`. Owner report: on iPad the app translates for a few seconds, then stops; the app is frozen, also while staying inside it.

**Nothing was compiled or run in chat.** The GitHub Actions run is the first real test. The fix is UNVERIFIED until it runs on the iPad. No speed claims; no hot path was edited.

## Evidence (iPad17,1, iOS 27.0.1, build 131)
- Eight ScreenLingo crash logs (2026-11-28): all `SIGKILL`, `0x8BADF00D` scene-update watchdog, main thread stuck 10 to 30 s. Every main-thread stack is SwiftUI layout of `TranslateScreen` (`body`, `heroBlock`, `sessionHero`), through `InsetViewLayout` (the compose-bar `safeAreaInset`) into `ScrollView` sizing, HStack/VStack.
- Two `cpu_resource` reports: 90 s of CPU in 140 s (64 %), same Translate layout frames.
- Test report: S4/S6 (2.7.0) died within seconds; S5 ran 1.1 min.
- The SpringBoard, IMDPersistenceAgent, backupd and Jetsam reports do not involve ScreenLingo.

## Cause (by reading code)
2.7.0 measured the width with `.onGeometryChange` on the Translate `ScrollView` and chose one or two columns from it. Inside the `safeAreaInset` the ScrollView's size depends on its content, and the content depends on the column choice, so the layout switched back and forth on every pass.

## Fix
- The width is measured once, on the `NavigationStack` (sized by the tab container, not by the page).
- `wide` is state, changed only in `measured(_:)`: on at 760 pt (1000 at accessibility sizes), off 60 pt lower; the width is rounded.
- Contract in `scripts/test_three_modes.py`.
