Base: `claude/screenlingo-v2.2.3`. Work branch: `claude/screenlingo-v2.3.0`. Draft PR into `codex/screenlingo-v1.9.9-recovery-evidence`, never `main`.

## Why diagnostics only
The b106 Legacy report could not answer the questions it raised, and part of it was mislabelled. Changing the hot path on that evidence would be guessing. 2.3.0 therefore does not touch translation, OCR, confirmation, the model choice, `process`, `drain`, `enqueue` or any default. `scripts/test_three_modes.py` (function-level equivalence with older commits) passes unchanged.

## Findings from the code (Legacy)
1. `pip_enqueue_legacy_recovery` is not a recovery. `context.fresh` means a confirmed-text model call was submitted. `mismatch` meant "the last unconfirmed sighting of ANY caption had different text", held in one shared value (`lastLegacySpeculation`). A caption with no early sighting of its own could be labelled recovery because of a neighbour. It is the same fresh translation, only slower on average in b106 (mean 696 ms vs 603 ms, unverified as a cause).
2. `recovery_service_ms` in Legacy was the ordinary confirmed model call (`confirmed_model_completed`). The same names are used by Low Latency (`ModeTranslationService.swift`); only in Hybrid do they mean recovery.
3. The Legacy caption-tag bookkeeping cleared all 128 entries at once. A caption whose translation was still running lost its `fresh` flag and could be reported as a memory hit, or its enqueue went unrecorded. b106 shows 14 such resets over about 1,850 candidates. Effect on the b106 numbers is likely small (the path counts add up to the 587 enqueues) but not measured.
4. `confirmed_continuity_loss` (166 in b106) counts confirmed captions replaced by a different confirmed caption before enqueue (`supersededUnpresentedConfirmed`, `TranslatorEngine.handleContent`). The caption table in the report shows 188 confirmed captions with no PiP enqueue, so at least 22 left some other way (clear, stale rejection, other). The gap to the next confirmed caption was similar for dropped and shown captions (median 879 ms vs 970 ms), and 45% of dropped ones had more than 1 s before the next caption. So "the subtitle changed too fast" does not explain them alone. UNVERIFIED which paths dominate.
5. The b106 report has no `legacyDetachedSpeculationReleaseMs` row, which is consistent with the 2.2.3 L2 switch (Legacy own lane) being OFF, but the report did not say. `speculativeStopReleaseMs` P50 212 ms (n=61) and `queueBehindSpeculationMs` P50 231 ms (n=109) are the cost L2 targets.
6. Apple documents `TranslationSession.cancel()` as "Attempts to stop all ongoing work", so a cancelled speculative call may keep running. This matches the code comment and the stop-release numbers.

## Not done, on purpose
- Turning on Legacy own lane (L2) by default: no on-device data with it ON; two simultaneous Apple Default calls may slow each other.
- Any change to when speculation starts or is cancelled: needs the new measurements first.
- No change to confirmation or OCR (the OCR P50 of 157 ms in b106 against about 105-115 ms earlier may be thermal Fair or the pixel check; unverified).
