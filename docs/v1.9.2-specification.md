# ScreenLingo v1.9.2 — Hybrid Reliability, Reuse and Performance Intelligence

**Implementation branch:** `codex/screenlingo-v1.9.2-hybrid-reliability`
**Source:** `codex/screenlingo-v1.9.1-hybrid-performance` (build 72)
**Target:** v1.9.2, build 73. Never modify `main`.
**Status:** Implementation and CI verification tracked separately; no claims of on-device performance without a fresh test.

## Evidence and priorities

The three v1.9.1 build-72 Portuguese→English temporary-memory exports show:
- Low Latency: median 230 ms, P95 433 ms, median speculative model 50 ms.
- Hybrid: median 465 ms, P95 1,665 ms, median speculative model 544 ms; confirmed median 55 ms but P95 1,619 ms.
- Legacy: median 511 ms, P95 930 ms; median speculative model 254 ms.
- Hybrid has prolonged cross-strategy overlap and extensive speculative misses. The OCR medians are 105–111 ms and rendering about 1 ms, so coordination and model resource behavior are the leading opportunities.
- All three report healthy persistent memory. Maintain the existing SQLite schema, migration, settings and privacy guarantees.

## Scope and implementation rules

1. **Hybrid-only speculation admission guard.** Do not start additional speculative Apple-default inference when an actual confirmed recovery, another speculative model request or warm-up occupies a backend lane. Preserve the original semantics: Apple-default ahead, Low Latency as confirmed/recovery, Apple-default fallback when fast assets are missing. Do not modify Legacy and explicit Low Latency behavior. Emit explicit no-admission diagnostics, distinct from user-disabled speculation and feedback throttling.
2. **Contention-aware backoff.** Adapt to repeated wasted/mismatching speculation and long overlapped recovery by temporarily favoring direct Low Latency translation. Backoff shall be bounded, deterministic, and reset by useful speculation, a mode switch, or capture reset; the optional adaptive-speculation switch still governs this feedback. Do not block confirmed recovery solely to keep a default-model session warm.
3. **Session-only reuse for completed translations.** Retain successful exact-key outputs from either strategy even if their caption subsequently became obsolete or lost a hedge race. Check preferred RAM/SQLite memory first; then the strategy-specific ephemeral session cache. Only valid, nonempty ordered results are eligible. Respect fresh-translation testing and reuse-disabled configurations; clear caches on capture reset and memory pressure, never write these speculative results to the permanent database, and bound memory with per-strategy FIFO limits. A stale caption must never regain display authority.
4. **Backend observability.** Report lane admission wait, fresh versus retained session, elapsed lifetime and real task dispatch, model execution, timeout, cancellation release and strategy overlap. Clearly distinguish measured service time from queue/overlap and warn that Apple's public API does not reveal model residency. Never infer zero from a missing measurement; no text, keys or user content in telemetry.
5. **Warm-up audit.** Record initial warm-up attempts, success/failure, strategy and duration in the same full-session counters and stage distributions used by new modes. Readiness means assets/sessions are checked, not that the model is physically resident. Preserve strict session invalidation and no parallel warm-up with live inference.
6. **Memory-safety and session boundaries.** Honor one physical model request per lane, callback cancellation, generation changes, mode switches, and missing installed languages. Validate permanent-memory integrity and ensure no repeated display of stale candidate output.
7. **Tests.** Cover backend-busy admission, backoff reset, stale-result cache reuse, cache isolation by strategy, memory-first priority, fresh-mode bypass, bounded eviction, timeout and winner/loser behavior. Maintain existing three-mode tests and diagnostic export tests.
8. **Version and CI.** Update the application and extension to 1.9.2 (73); run Swift regression suites and the macOS IPA workflow. Publish as a PR and retain Legacy and Low Latency as user-selectable modes.

## Acceptance gates

- No regression in build, app launch, language switching, capture readiness, PiP identity, imported/persisted memory or current settings.
- Compare equal-length, same-content, same-device tests using identical OCR region, pair, temp-memory baseline, thermal conditions and run order balancing. At least three trials per mode, with warm and cold runs.
- Primary goal: Hybrid median <= Legacy median **and** Hybrid P95 <= Legacy P95, with no translation-completeness, flicker or resource-use regression; long-term aspirational goal is to approach standalone Low Latency without sacrificing Apple-default wording.
- Report fingerprint-matched OCR-to-PiP median/P90/P95, completion coverage, recovery overlap counts, model service distributions, stale outputs, session caches and admission skips.
- If gates fail, keep Hybrid experimental and explain measurements; never claim the branch is faster based on theoretical reasoning alone.

## Compatibility and API assumptions

Apple's `TranslationSession` `preferredStrategy` and `isReady` do not guarantee physical model residency. Low Latency uses explicit installed-language resources on supported iOS versions. Apple-default fallback and older OS handling must remain operational; no private API, no self-hosted service, no changes to permanent memory schema or keys.
