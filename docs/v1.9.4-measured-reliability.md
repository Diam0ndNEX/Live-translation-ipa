# ScreenLingo v1.9.4 — measured reliability candidate

## Release decision
v1.9.4, NOT v2.0.0. No measured evidence supplies at least 90% confidence that a performance rewrite would improve Legacy, Hybrid Recovery, and Low Latency simultaneously. Do not claim universal performance improvements from this candidate.

## Device baseline (30 October 2026)
Three uploaded Portuguese → English Balanced / Temporary Memory diagnostics (the app metadata reports v1.9.3 build 74):

| Mode | median OCR→PiP enqueue | mean | P95 | successful enqueue samples |
| --- | ---: | ---: | ---: | ---: |
| Legacy | 550 ms | 574 ms | 1,017 ms | 89 |
| Hybrid | 382 ms | 542 ms | 1,409 ms | 77 |
| Low Latency | 232 ms | 281 ms | 442 ms | 84 |

These are observations, not performance promises. An enqueue is not physical screen presentation. Tests were not perfectly matched for cache snapshots, thermal chronology, or subtitle frequency.

## Implemented in this candidate
- Version and build synchronized to v1.9.4 (75) for app and extension, with changelog and matching source-contract tests.
- Count real warm-up model submissions as warmupAttempts and successful completed warm-up operations as warmupSucceeded in the common Diagnostics counter stream, regardless of the selected pipeline. Failed or skipped claims do not produce success counts. Preserve separate per-strategy duration metrics, retained warm-up event trace, and warmupModelBatches.
- Add regression assertions for the common warm-up event wiring.
- Preserve Legacy scheduler, Hybrid coordinator, Low Latency speculative and confirmed scheduling, persistent memory schemas, temporary memory rules, and PiP result selection. No speculative claim of speedup from a telemetry-only change.

## Next engineering investigation (not implemented)
Hybrid retained-session Low Latency recovery has approximately 47 ms median but 1,568 ms P95 service, while standalone Low Latency speculative service is around 45 ms median / 64 ms P95. Prioritize tracing physical backend lane occupancy, cancellation-to-return, default speculation overlap, and whether simultaneous strategy sessions compete for internal translation resources. Do not confuse software queue waiting with internal backend service time.

Instrument and test one hypothesis at a time on a separate experimental branch. Disable or reject changes if Legacy or Low Latency regress. Preserve warm session state safely; do not force session cancellation on every caption or introduce unconditional hedges. Diagnose and repair export manifest membership of translation_modes.json separately after inspecting archive writer and reader contracts.

## Required release acceptance (not yet satisfied)
1. Full macOS GitHub CI including Swift/SQLite/transport/diagnostics tests, app/extension Release compilation, and IPA packaging.
2. Three comparable ≥5 minute on-device tests per mode using same source video, language, capture settings and balanced counterbalanced test order. Record cold/warm and fresh/reused caption groups separately.
3. Compare p50, p90, p95, P99 when sample count allows, measured OCR→PiP enqueue, actual model service time, displayed caption coverage, first-line retention, flicker, errors and battery/thermal.
4. Reject any candidate that has meaningful regression in Legacy or Low Latency; require Hybrid P95 < 1,409 ms and preferably < 600 ms before claiming improved Hybrid tail consistency.
5. Preserve persistent memory, provenance, schema, history, bundle identity and in-place installation; Temporary Memory must not durably store translations.
6. The v2.0.0 decision requires independent evidence supporting at least 90% confidence of faster real-device performance in **all three modes**, without quality or memory regressions. At present this gate is not met.

## Status
Code candidate only; successful build, IPA and physical-device performance are not established by this document. Do not merge to main solely on the basis of instrumentation changes.
