# ScreenLingo 2.2.1 – Fix, verify and instrument (specification)

Status: written 2026-11-08 from a read-only code review of `claude/screenlingo-v2.2.0` (commit 7d99ce6, build 103).
Owner decisions of 2026-11-08 are folded in (see `docs/v2.2.1-decisions.md`, which stays the record of what was decided).
Nothing was compiled or run. Every item below says what was read; anything not proven is marked **unverified**.
This document changes no code. Version: **2.2.1 build 104** (confirmed by the owner).

## 0. Why this update

The 2.1/2.2 work rebuilt the screens. The review of the whole app (UI, engine, capture extension, Hybrid model service,
memory store, PiP renderer, diagnostics recorder and export) found three groups of problems:

1. **Things that lose data or give wrong results** (saved Library items deleted, Resume that does not stick, a capture that
   is paused while the header says Live).
2. **A test pipeline that can produce a run that looks valid but is not** (no median when Detailed collection is off, save
   results nobody can see, runs polluted by manual translations, comparisons that are almost always withheld).
3. **Settings and buttons that do not do what they say** (Content menu, a dead toggle, a spinner that never stops, onboarding
   that still opens the floating window with the capture sheet).

The goal of 2.2.1 is that the **next three-mode device test produces data that can be trusted**, that every control does
what its label says, and that A/B tests no longer need a separate build per variant. It is not a speed update.
**No speed claim may be made from this update without Diagnostics data from all three modes** (project rule).

- Branch `claude/screenlingo-v2.2.1` from `claude/screenlingo-v2.2.0` (already created; it holds this spec). Draft PR into the

  Several compare whole functions or exact source lines (see §6).

  and `ModeTranslationService` may be edited when the evidence supports it. Rule that replaces the freeze: when a contract test
  asserts an exact source line you change, update that assertion **in the same commit** and say in the commit message and in the
  PR which assertion changed and why. Never delete an assertion just to get a green build.
- Settings keys, defaults and stored formats stay (new keys may be added with defaults that equal today's behaviour).
  Privacy stays metadata-only.
- One work package per push. After each push read the CI log yourself (`gh run view <id> --log-failed`) and fix compile errors
  before the next package. Do not poll CI; the owner reports results.
- Version 2.2.1 build 104 in `Shared/Shared.swift` (version, build, changelog entry) and `project.yml` (3 places each) and in
  every script that asserts it: `scripts/test_v199_performance.py` (version, build, `project.count`), and the two others that

- Say in every report that nothing was compiled or run in chat. Mark **device check** for anything only the phone can confirm.
- If a real problem not listed here turns up, add it to the PR list with evidence; fix it when small and safe, ask when large.
