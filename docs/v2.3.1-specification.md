# ScreenLingo 2.3.1 (build 108): the same diagnostics names in every mode

Status: written 2026-11-10 after the owner asked for inconsistent names across modes to be sorted. Nothing here was compiled or run. No speed claims. Base: `claude/screenlingo-v2.3.0`; branch `claude/screenlingo-v2.3.1`; draft PR into `codex/screenlingo-v1.9.9-recovery-evidence`.

## Correction to 2.3.0
2.3.0 said Low Latency's `recovery_*` names were a misnomer. They are not. In Hybrid Recovery and Low Latency, `TranslationSystem.startRecovery` is the only place a translation after confirmation is requested (memory missed and the early translation could not serve), and its non-speculative `resolve` call is the recovery. Legacy has the same situation but never had the word. The wrong README sentence is replaced; the 2.3.0 changelog line is marked as wrong.

## What the modes call the same thing
| Source of the caption | Legacy | Hybrid Recovery / Low Latency |
|---|---|---|
| Stored result | `pip_enqueue_memory_hit` | `pip_enqueue_memory_hit` |
| Early translation, finished | `pip_enqueue_speculation_match_ready` | `pip_enqueue_speculation_match_ready` |
| Early translation, still running | `pip_enqueue_speculation_match_in_flight` (new in 2.3.1) | `pip_enqueue_speculation_match_in_flight` |
| Translated after confirmation | `pip_enqueue_confirmed_fresh`, or `pip_enqueue_fresh_text_changed` | `pip_enqueue_recovery_success` (reason `recovery_decision_*`) |
| Confirmed-time model call time | `confirmed_service_ms` | `recovery_service_ms` |

The model-call table lane (`confirmed`) and `confirmedModelMs` are the same in all modes.

## Changes
- Report: three groups summed over languages in every mode, `path_memory`, `path_early`, `path_confirmed_time` (service and confirmation-to-enqueue). README table explains them.
- Legacy: new `speculation_match_in_flight` label when the early translation of exactly the confirmed text was still running at confirmation (one diagnostic call in `enqueue()`, next to the existing counter).
- Hybrid and Low Latency: a unit with no result is recorded as `bypassed` (not `miss`) when memory reuse is off (`memoryTestMode.allowsReuse && !bypassMemory`), as Legacy already did.
- Version 2.3.1 build 108; `scripts/test_v231_contracts.py` in CI; `test_v230_contracts.py` README assertion replaced (it asserted the wrong sentence).

## Not changed
Per-unit origin strings (`compatible_memory`, `session_*`, `speculation`, `recovery`, `fresh`) exist only in Hybrid and Low Latency; they already map onto the shared memory outcomes (`ramHit`, `persistentHit`, `legacyHit`, `normalizedHit`, `speculativeHit`, `miss`, `temporaryMiss`, now `bypassed`). Legacy has no per-unit origin string; adding one means touching `process()`, which `test_three_modes.py` freezes. UNVERIFIED whether it is worth it.
