## 1. The main finding: where the time goes (all modes)

1. **The measured boundary starts at the start of the OCR read that first saw the final text.** READ-IN-CODE: `firstSeenAt` is the tracker's
   `first`, set to `readStartedMonotonic` of that read (`SampleHandler.admit`, `SubtitleTracker.observe`).
2. **The "125 ms confirmation" is not a second stage after a 120 ms OCR stage. It contains the OCR pass.** READ-IN-CODE: pixel confirmation
   needs `elapsed since first read start >= max(0.1, interval)`, and with a pending caption `interval = max(0.10, last OCR time)`
   (`SubtitlePerformancePolicy.confirmationInterval`). So the dwell ends when the OCR pass ends, and the first frame after it confirms.
   INFERRED from the captions table: confirmed minus first sighting is P50 123 to 129 ms while one OCR pass is P50 117 to 125 ms. The floor every
   caption pays is therefore about **one OCR pass (about 120 ms) plus about 5 ms**, not 245 ms.
3. **The early ("first sighting") packet reaches the app about 1 to 5 ms before the confirmed packet.** INFERRED: in section 4 of the report the
   matched speculative call starts within 1 ms of `confirmed_ms` in every case checked (S1 c12, c15, c23, c35, c47, c48, c54, c60, c76; S3
   throughout), also when the track was first seen 200 to 300 ms earlier. READ-IN-CODE reason: the tentative packet is sent when the text of
   a read differs from the last tentative text; the read that first has the final text is confirmed by pixels one frame later.
   **So translate-ahead buys about 0 ms of head start in 2.3.9.** Low Latency's "90 of 96 early" captions waited the full 48 ms model call after
   confirmation (confirmation to enqueue P50 51 ms).
4. **What translate-ahead costs.** INFERRED: S1 has 319 candidate ids for 114 confirmed captions, so about two thirds of tentative reads are
   never confirmed (text still changing, or scene text). Each of those that starts an Apple Default call (about 270 ms, not cancellable in
   practice: stop release P50 128 ms, max 629 ms) occupies or overlaps the lane exactly when the real caption is confirmed about 125 ms later.
   This is the source of Legacy's overlap (307 ms alone, 511 ms overlapped), session switch (302 vs 511 ms), queue-behind-speculation (P95 333 ms)
   and stop-release waits. For the 48 ms Low Latency model the same waste is harmless.
5. **Per-mode floor with the present design** (INFERRED, P50): Legacy = OCR 120 + Apple Default about 270 to 300 + overhead = about 400 to 430 (measured
   453). Low Latency = OCR 125 + model 48 + overhead about 10 = about 185 (measured 189). Hybrid = Legacy's floor for the two thirds of
   captions served by Apple Default (measured 453).

Consequence for the goals: Low Latency P50 under 150 and Legacy P50 under 350 are **not reachable without a faster OCR pass** (or, for Legacy, a
model call that starts before OCR ends). No 2.4.0 change is claimed to reach them. See section 5.

## 3. Capture extension (SampleHandler)

1. **Hidden latency before the boundary: cadence.** READ-IN-CODE: with no caption on screen the next read waits for the cadence (0.22 s for
   Balanced) or an early visual wake (not before 72% of the interval, at most two per second). A new caption is therefore first read 0 to about
   220 ms after it appears. This time is not inside "first OCR sighting to PiP". UNVERIFIED size; `lastVisualChangeAt` gives a proxy.
2. **Hidden latency before the boundary: focused crop.** READ-IN-CODE: in Hybrid and Low Latency (`focusedCaptionOCR`), a focused read whose
   text differs from the previous read is thrown away (`requiresRediscovery`) and the whole area is read again. The thrown-away read is not a
   first sighting, and because no candidate is pending the next read waits for the ordinary cadence. So a new caption can cost one extra OCR
   pass plus up to about 100 ms that Diagnostics never sees. INFERRED: the crop does not make OCR measurably faster in the report (OCR P50
   121 ms without it in S1, 117 and 125 ms with it in S2 and S3), most likely because nearly every read of a new caption is a broad read.
3. **Frames during OCR are dropped** (`recognitionLock.try()`), so confirmation uses the first frame delivered after the pass. READ-IN-CODE.
   Whether ReplayKit delivers that frame at once or one frame interval later is UNVERIFIED.
4. **Pixel confirmation and the caption watch re-read orientation and build two `CIImage` values per check.** READ-IN-CODE. Small cost
   (384 point reads); not a floor item.
5. **OCR request**: `.accurate`, language correction on, `VNImageRequestHandler(ciImage:)` on a cropped, scaled `CIImage`. READ-IN-CODE.
   Passing the pixel buffer with `regionOfInterest` would skip a Core Image render; effect UNVERIFIED and it changes how rotation is applied.
6. **Every packet is a JSON object with about 45 keys**, encoded on the capture thread. READ-IN-CODE. Cost not measured; small next to OCR.
7. **Risk**: `processSampleBuffer` holds `recognitionLock` for the whole OCR pass and `broadcastFinished` takes the same lock, so stopping
   waits for a running pass. READ-IN-CODE. Acceptable.
8. **Risk**: `sampleLuma` assumes plane 0 is luma or the buffer is BGRA; other formats return nil and fall back to OCR. READ-IN-CODE, safe.

## 4. App: hot path, queues, sessions

1. **Diagnostics on the main actor, in the critical path.** READ-IN-CODE:
   - `structuredEvents` is `@Published` and holds up to 6000 structs. `append` through a published property is get, mutate, set, so the array is
     copied on every event, and `removeFirst` shifts 6000 elements again once the ring is full. With Detailed collection on (the owner's
     test setting) a caption produces many such events before its model call starts. Cost per event UNVERIFIED (estimate: tenths of a millisecond).
   - `modeTrace` shifts up to 6000 elements per event once full (`removeFirst`).
   - `Diagnostics.noteModeEvent` computes SHA-256 of the caption id and formats 32 hex bytes with `String(format:)` for **every** mode event
     (tens per caption).
   - `Diagnostics.tick` filters all structured events once a second in Detailed mode.
2. **An extra main-actor hop before each Hybrid/Low Latency model call.** READ-IN-CODE: `ModeTranslationService.translate` starts the Apple call in
   a new `Task { @MainActor in ... }` inside a continuation. The report's `modeTaskDispatchMs` is that hop: P50 1 ms, but P90 17 ms (Hybrid) and
   34 ms (Low Latency), P99 48 ms. INFERRED: the wait is other main-actor work queued first (next packet, diagnostics).
3. **Availability check on the request path every 30 s** (`installedCheckTTL`), about 46 ms when it runs (P99 of `modeAvailabilityCheckMs`). The
   background refresh switch from 2.2.3 exists and is off. READ-IN-CODE.
4. **Lane waits poll every 5 ms** (`while lane.busy { sleep 5 ms }`). READ-IN-CODE. Adds 0 to 5 ms after a lane frees.
5. **Legacy** (READ-IN-CODE): one serial drain. A tentative packet starts `process(display: false)` on a leased speculative session. A confirmed
   packet with different text cancels that session and either waits for it to unwind or, with `legacyConfirmedOwnLane`, starts at once on the
   direct session while the cancelled call still runs. A cancelled lease is never reused, so the next speculation builds a new session.
   The adaptive governor (`SpeculativeWorkWindow`) halves opportunities only after 24 attempts with at least 50% discarded and under 18% reused.
6. **Hybrid** (READ-IN-CODE): Apple Default on the speculative lane, recovery on the confirmed lane with Low Latency or, inside the 1.5 s switch
   guard, Apple Default; hedge suppression waits up to 1.2 s for a matching Default call; a drain budget (0.45 s) and a settling wait (0.22 s)
   before Low Latency. All of it exists to soften the model-change cost that section 2 shows is paid anyway.
7. **Low Latency** (READ-IN-CODE): same coordinator, both lanes Low Latency. A new confirmed caption cancels the previous confirmed session
   (`session.cancel()`), which invalidates the lane's session and creates a new one on the next call. Not seen in S3 (calls are short).
8. **Defects and risks found** (READ-IN-CODE unless marked):
   - `ThreeModeCoordinator.observe` drops a tentative caption when a speculation is already running (`speculation == nil` guard). In Low Latency
     a second tentative within about 50 ms is lost and its confirmation takes the recovery path. Small.
   - `modeConfirmationUptime`, `modeResultReadyUptime`, `modeModelTimings`, `modeFingerprintDigests`, `recentSQLiteProbes`, `modeMemoryOrigins`
     are bounded by "clear everything at N" rather than oldest-first; a clear in the middle of a caption loses that caption's timing rows.
   - `handleModeCaption` writes several `@Published` values per packet (`isTranslating`, `detectedLang`, `latestBlocks` is not published);
     each fires `objectWillChange` for every observer of the engine. Cost UNVERIFIED.
   - `detectSource` runs the language recognizer up to three times per confirmed caption in Automatic source (cached per text, 128 entries).
   - `LoopbackServer` creates one `Task` per packet on the main actor with `.userInitiated`; ordering between two packets sent 1 ms apart is
     not guaranteed by the language. INFERRED risk: a confirmed packet could be handled before its tentative packet. Harmless today.
   - The hosted (iOS 18) path polls `hostedTask` every 20 ms and has a 10 s timeout; not used on the test device.
   - No retain cycles were found in the files read; long-lived closures capture `self` weakly. Not checked in unread files.

## 4b. Memory path (read after 2.4.0 was built; added for completeness)

Read: `TranslationMemoryStore+Lookup.swift`, the lookup and statement code in `TranslationMemoryStore.swift`, and `queueMemory`, `saveMemory`,
`flushPendingMemory`, `trimCache` in `TranslatorEngine+Memory.swift`. Not read: migration, recovery, import/export, legacy idle validation.

1. A persistent lookup is one hop to the store actor, one indexed query, and a second (normalized) query on a miss, with an 8 ms limit that
   includes waiting behind other actor work. READ-IN-CODE. In the device test (Temporary Memory) persistent lookups are off, so the report's
   0 ms says nothing about Normal memory. UNVERIFIED for Normal memory.
2. Saves, health queries and lookups share one actor and one connection. A lookup that waits behind a save for more than 8 ms returns
   "timeout" and the caption is translated fresh. No wrong text, but a lost memory hit and up to 8 ms on that caption. READ-IN-CODE. The
   owner's earlier idea (a second read-only connection) stays the fix if `memoryLookupWaitMs` shows waiting in a Normal-memory run.
3. Each lookup creates a timer block and a task. Small. READ-IN-CODE.
4. `trimCache` scans all use stamps (up to 3000) for each insertion once the RAM bank is full, on the main actor. INFERRED small; not measured.
5. A save starts 75 ms after the first queued entry and ends with a health query on the store actor. READ-IN-CODE.
6. Low Latency results are never written to RAM or SQLite memory (`where output.strategies[i] == .appleDefault`). With Hybrid pinned to Low
   Latency in 2.4.0, Hybrid therefore stops adding to memory. READ-IN-CODE.
No memory code was changed in 2.4.0.

## 6. Refinement options and test gaps

- `handleContent` (229 lines) and `process` (391 lines) remain single functions guarded by text-equality tests against commit e94542ce.
  2.4.0 edits `handleContent` and leaves `process`, `drain` and `cachedCaption` untouched.
- Python contract tests check that strings exist in sources; they cannot catch a logic error. Real behaviour tests exist only for the
  coordinator, policies, memory store, archive and transport (Swift programs in `Tests/`, compiled in CI only).
- There is no test of the capture extension's scheduling (`processSampleBuffer`), of `ModeTranslationService` (needs the Translation framework) or of
  the Legacy drain.
- Diagnostics label check (owner request): the Legacy enqueue labels were already corrected in 2.3.0 (`pip_enqueue_confirmed_fresh`,
  `fresh_text_changed`, `speculation_match_*`). Still misleading in 2.3.9: (a) the stage names `finalOCRMs` and `confirmationMs` read as two
  stages in sequence although the second contains the first (1.2); (b) `path_early` suggests a head start that does not exist (1.3);
  (c) `speculative` in the lane column for a call that started at confirmation. 2.4.0 adds notes to the report and new rows instead of renaming, so
  old and new reports stay comparable.
- Not audited (not read): UI, test run store, memory store internals, simulator. No claims are made about them.
- What 2.4.0 built from this audit, and what it left out, is in `docs/v2.4.0-specification.md`.
