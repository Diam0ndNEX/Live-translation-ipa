# ScreenLingo v2.0.0 (build 83): specification

## 0. 2.0.0 rethink (2026-11-06): rebuild the critical path for all modes

The first draft below (§1–§10) mostly targeted Hybrid. A 2.0 release should change where the time goes in
every mode. Nothing here is compiled or measured; every effect is **unverified** until a same-video Diagnostics
run of all three modes shows it.

### Where the time goes today (device data, builds 74–82)
| Stage | Time | Modes |
|---|---|---|
| First OCR read (`.accurate`) | ~95–115 ms | all |
| Second OCR read, only to confirm the text is stable | ~115–135 ms | all |
| Apple Default (= Apple Intelligence on this iPhone) call after confirmation | ~275–300 ms (~70% of Legacy captions) | Legacy |
| Low Latency recovery near Default work | ~900–1200 ms | Hybrid |
| Confirmation → PiP | ~28 ms | LL, Hybrid |

### Research findings
- **"Apple Default" is Apple Intelligence.** For apps built with the iOS 26.4+ SDK, `TranslationSession` without a
  strategy uses `highFidelity` (Apple Intelligence) on supported devices; `lowLatency` is the traditional model,
  which Apple describes as faster and lower power. The CI uses Xcode 26.6, so on iPhone18,2 "Apple Default" is the
  Apple Intelligence model. This fits the data: ~6× slower than LL, and a ~1 s penalty when alternating models
  (likely model swap / Neural Engine contention; not proven).
- **iOS 27 `.accurate` OCR regression** reported on Apple's forums (thread 851862): missed strings,
  upside-down reads, junk characters; `.fast` unaffected; no Apple reply. The device runs iOS 27.0.1.
- **OCR and translation share the Neural Engine.** `.accurate` OCR is a neural network and runs about every
  100 ms in the extension, in parallel with translation models. Fewer OCR passes should reduce contention and heat
  (hypothesis).
- Vision guidance: limiting the region of interest, raising `minimumTextHeight`, `.fast`, and turning off language
  correction all speed recognition.

### Giant changes (proposed)
- **G1. Pixel-verified confirmation (all modes).** After the first OCR read of a new caption, confirm it when the
  pixels inside its text boxes stay unchanged for the same minimum dwell the second read uses today (≥ the OCR
  interval, 100 ms minimum), checked on every captured frame. Continuous pixel stability is at least as strong as two
  samples 100 ms apart; a second OCR read is still done whenever the pixels change. Expected: removes the ~115 ms
  second read from the critical path in every mode (LL ~240 → ~130 ms). Risk: a tiny text change missed by the
  signature; mitigated by a fine grid over the line boxes and by the existing source-correction path. Toggle for A/B.
- **G2. Event-driven OCR (all modes).** No OCR while the caption region is pixel-identical to the last read (only a
  slow heartbeat); OCR immediately when pixels change. Fewer Neural Engine passes, less heat, and less contention with
  translation models.
- **G3. Faster OCR input.** Pass the `CVPixelBuffer` with `regionOfInterest` and orientation to Vision instead of a
  CoreImage crop/scale per pass. Add an experimental **Fast OCR** engine (`.fast`, no language correction), off by
  default, because of the iOS 27 `.accurate` report.
- **G4. Hybrid model switch guard** (done: H1–H3, H5 below). Keeps Default prediction + LL recovery, except inside the
  measured switch window.
- **G5. Legacy: one Apple Default session** for prediction and confirmed work, and wider prediction at Nominal/Fair.
  Needs an update of the frozen-function test (`test_three_modes.py`, commit e94542ce).
- **G6. Low Latency / Hybrid handoff:** trim the ~28 ms confirmation→PiP path (main-thread hops, memory probe wait).
- Done in this branch already: L1–L3 diagnostics, S1–S4, one-file test report, Home buttons and mode switch.

## 1. Where the time goes (device data, builds 74–82)

OCR → PiP enqueue, median: Low Latency ≈ 240 ms, Legacy ≈ 500–550 ms, Hybrid ≈ 570–680 ms (382 ms at build 74).
OCR (~100 ms) and confirmation (~115–135 ms) are flat across builds and modes. The differences are in the model stage.

| Mode | Critical path today | Main waste |
|---|---|---|
| Low Latency | OCR + 2nd confirming read + ~28 ms confirmation→PiP | Little. The ~44 ms model call finishes before confirmation. |
| Legacy | ~70% of captions run a confirmed Apple Default call (~275–300 ms) after confirmation | Speculation covers too few captions; cause not yet measured. |
| Hybrid | Low Latency recovery after or during an Apple Default call: ~900–1200 ms instead of ~40 ms | Switching between the two models (§2). |

## 2. Hybrid Recovery: the main 2.0.0 change

### Problem
A Low Latency recovery takes ~40 ms when no Apple Default call is near, ~1,100 ms when one is running, and ~930 ms
when one finished less than ~1.5 s earlier, at thermal 0 and 1. From build 77 on, Hybrid sends ~3× more Apple Default
speculation, so most recoveries pay this. Build 78 (v1.9.6) sent recovery through Apple Default and avoided the switch:
530/872 ms. The cause (model reload or Neural Engine contention) is not proven.

### What v1.9.9 already does, and why it is not enough
- `physicalDrainBudget`: waits ≤450 ms for a running Default call before a Low Latency recovery.
- `postDefaultSettlement`: waits ≤220 ms if a Default call returned <220 ms ago.

The penalty was seen up to ~1.5 s after a Default call, so these waits add delay without avoiding most of it.
(The v1.9.9 retrospective saw the worst cases within 150 ms; the gap curve between 150 ms and 1.5 s needs the next
export.) Build 82 had no Hybrid run, so their effect is unmeasured.

Two code paths make it worse:
1. **The hedge** (`observe` → deadline task → `hybrid_hedged_recovery`): while the matching Default speculation is still
   running, Hybrid starts a Low Latency recovery in parallel. That is the slowest kind of recovery (~1,100 ms), while the
   Default call usually finishes in ~250–450 ms. The hedge rarely wins.
2. **Obsolete speculation keeps running** (`hybrid_obsolete_speculation_draining`): a Default call for text that was
   not confirmed keeps running, and the next Low Latency recovery pays the switch.

### H1. Switch guard
In `ThreeModeCoordinator.startRecovery`, Hybrid picks the recovery strategy per caption:
- An Apple Default call is **in flight**, or **returned less than `hybridSwitchGuardMs` ago** (default 1500, same
  language pair) → recover with **Apple Default**.
- Otherwise → recover with **Low Latency** (keeps the fast ~40 ms case).
- Low Latency pack missing → unchanged (Default).
- The one-time Default fallback after a failed Low Latency recovery stays.

Wiring: add a coordinator closure such as `var appleDefaultGapMs: () -> Double?` (0 = in flight, nil = none recent),
set in `TranslatorEngine` from `ModeTranslationService` (`speculative.busy`, `requestedStrategy`, `lastFinishedAt`,
`lastFinishedPair`). Put the decision in a pure static function in `HybridSchedulingPolicy` (e.g.
`recoveryStrategy(gapMs:fastRecoveryInstalled:guardEnabled:)`) and test it in `Tests/ThreeModes/main.swift`.

Events: `hybrid_switch_guard_default` (gap ms) and `hybrid_switch_guard_low_latency` (gap ms or none).

### H2. No parallel hedge in Hybrid
If the matching Default speculation is still running at confirmation, wait for it (existing matching-wait logic,
ceiling 1.2 s) instead of starting a parallel Low Latency call. If it fails or the deadline passes, start recovery
through H1, which will pick Default. Event: `hybrid_hedge_suppressed`.

### H3. Confirmed lane keeps one session per strategy
`ModeTranslationService.install` keys the confirmed lane by strategy, so alternating Default and Low Latency recoveries
would recreate the `TranslationSession` each time. Keep up to two sessions in the confirmed lane (one per strategy) and
reuse the matching one. Keep reporting `retained_session_start` / `new_session_start`.

### H4. Keep the v1.9.9 waits
`physicalDrainBudget` and `postDefaultSettlement` only apply to Low Latency recoveries after Default, which H1 mostly
removes. Do not delete them: `test_v198_performance.py`, `test_v199_performance.py` and `Tests/ThreeModes` assert them.
Their events will show how often they still fire.

### H5. A/B toggle on the device
CI produces one IPA, and the `SCREENLINGO_REFERENCE_*` flags only affect test binaries. Add an Experimental Features
toggle `hybridSwitchGuard` (default **on**) that turns H1 and H2 off, so the same IPA can run a comparison. Follow the
`directPiPBuffer` pattern (`ExperimentalFeaturesView`, `TranslatorEngine.defaults` and `interfaceKeys`) and update
`scripts/test_experimental_settings.py`, which lists the experimental keys.

### Expected effect (unverified)
Hybrid around build 78 (~530 ms median) or better, with a much smaller tail, because isolated Low Latency recoveries
stay at ~40 ms. Risk: more Apple Default work in total, and the speculative and confirmed lanes may both run Default at
once. Build 78 did this without an obvious penalty, but it was not measured separately.

## 3. Legacy: measure in 2.0.0, change in 2.0.1

Legacy's model path is frozen: `scripts/test_three_modes.py` requires `process`, `drain`, `cachedCaption`,
`extractTexts` and `selectBlocks` to match commit `e94542ce` byte for byte. Changing them needs explicit approval and a
test update, so 2.0.0 does not touch them.

What the code shows:
- Speculation uses a separate Apple Default session (`speculativeSessions`); confirmed work uses `directSession`.
  Confirmed calls are slower than speculative ones (P50 ~275–300 vs ~240 ms). Alternating between two sessions of the
  same model is one possible cause. **Unverified.**
- Speculation is skipped when the lane is busy, on low OCR confidence, and by the adaptive governor
  (`speculationWindow`; 70 skips in v1.9.6). A cancelled speculative session is not reused, so the next one is new.

2.0.0 adds diagnostics only:
- **L1.** Share of confirmed captions served by speculation, RAM, SQLite, or a confirmed model call, as one summary line.
- **L2.** Confirmed model duration split by "previous model call was on the other session and ended < 1.5 s ago" vs not.
- **L3.** Speculative sessions created per minute (`speculative_session_created` exists; add it to the summary).

With that data, 2.0.1 can pick between one shared Legacy session, a looser governor at Nominal/Fair, or no change.

## 4. Low Latency: near its floor

Critical path: OCR (~100 ms) + the second confirming read (~115 ms; interval = last OCR time, minimum 100 ms) +
~28 ms confirmation→PiP. Shortening confirmation is not allowed (never weaken OCR confirmation).

2.0.0: no algorithm change. Analysis task on the next export: split the ~28 ms using existing events
(`memory_lookup_start/end`, `speculation_match_unfinished`, `mode_ready_to_pip_ms`, `mode_confirmation_to_pip_ms`).
The SQLite probe times out at 8 ms, so most of the 28 ms is probably waiting for speculation or main-thread hops.

## 5. Small safe changes (all modes)

These remove main-thread work without changing results. The gain is likely under 1 ms per caption; do not claim a
speed-up from them.

- **S1. `selectModeResult`** (Hybrid and Low Latency, source = auto only): `languageEvidence` runs once per Apple
  Default unit before `show()`. Compute it once per caption, and queue memory writes after `show()`. Keep what
  `test_mode_diagnostics_ui.py` asserts (`queueMemory(`, `if presented {` before `diag.recordModeSelection(`).
- **S2. `show()`**: two `UserDefaults` writes per subtitle (`lastEffectiveSource`, `lastEffectiveSourceAt`). Write the
  source only when it changes, the timestamp at most every 30 s.
- **S3. `SampleHandler.processSampleBuffer`**: the thermal/pressure expression is built twice per frame. Compute it
  once. Keep the literal `ThermalPerformancePolicy.automaticPressure(for: ProcessInfo.processInfo.thermalState)` that
  `test_thermal_parity.py` looks for.
- **S4. Packet size** (correctness): `SampleHandler.send` only trims above 60,000 bytes, but loopback UDP datagrams
  over ~9 KB may fail on iOS, and the send error is ignored. Trim lines until the packet is under 8,000 bytes and count
  send errors in diagnostics. Only very text-dense screens are affected.

Dropped from the earlier review: making `directPiPBuffer` the default. Model-ready→PiP is ~1.2 ms, so rendering is not
a bottleneck.

## 9. Diagnostics: one combined text report

Today each mode run is exported as its own ZIP (11 files). A three-mode test is three ZIPs that have to be unzipped
before anything can be read. 2.0.0 adds a **combined report**: one plain-text Markdown file for several sessions.
The ZIP export stays for deep debugging.

### What the user does
1. Keep "Save diagnostic sessions" (`persistDiagnosticSessions`) on while testing.
2. Run the three modes (routine below).
3. Diagnostics → **Export test report** → the app preselects the newest saved session of each mode (user can change
   the selection, up to 6 sessions) → one share sheet with one file.

### File
`ScreenLingo-Report-<version>-b<build>-<yyyyMMdd-HHmm>.md`, UTF-8, target under 150 KB for three 5-minute sessions.
No subtitle text, OCR text or video, same redaction as `session.json` (`redact(_:)`); opaque IDs only.

Contents, in this order:
1. **Header**: app version/build, device model, iOS, language pair, preset, effective recognition switches
   (`rapidTextTracking`, `joinAdjacentText`, `activeTextFocus`), memory cohort (Temporary/Normal/Fresh), speed, the
   `hybridSwitchGuard` setting, each session's starting RAM entries (`diag.startingRAMEntries`, flagged when a run
   started with test memory already filled), and a content fingerprint overlap between the selected sessions (share of
   matching caption fingerprints, so the reader can see whether the same video was used).
2. **Comparison table**, one row per session: mode, duration, thermal states seen, enqueues (n), OCR→PiP P50/P90/P95/P99/max,
   OCR P50, confirmation P50, model P50 by strategy and lane, memory hits/misses, PiP failures, events dropped by the cap.
3. **Per-mode stage table**: the existing `metrics.csv` rows (stage, n, mean, P50, P90, P95, P99, max) as a Markdown table.
4. **Model calls** (CSV in a fenced block, one row per real model call, all sessions):
   `session,mode,lane,strategy,speculative,start_ms,end_ms,service_ms,queue_ms,warm,caption_ref,outcome`
   with times in ms from session start, rounded to 1 ms. This is what the Hybrid switch analysis needs.
5. **Captions** (CSV): `session,caption_ref,first_ocr_ms,confirmed_ms,selected_ms,pip_ms,reason,origin,strategy,recovery_strategy,guard_gap_ms`.
6. **Hybrid decisions** (CSV): recovery decisions, `hybrid_switch_guard_*`, `hybrid_hedge_suppressed`, drain and
   settlement waits, with times and durations.
7. **Findings**: the existing `findings.json` items as short lines.
8. **Truncation**: events retained/dropped per session, and whether the 2,400-event cap was hit.

Implementation notes:
- Build it in `DiagnosticArchive.swift` next to `exportZIP` (e.g. `exportCombinedReport(_ sessions: [DiagnosticSessionExport])`),
  from the same redacted snapshots. Reuse the existing percentile and CSV helpers.
- Saved sessions come from `loadSessions()`; the current live session can be included without saving it.
- Numbers: fixed precision (ms with 0–1 decimals), no full-precision doubles, to keep the file small.
- Add a Swift test in `Tests/DiagnosticArchive/main.swift`: three synthetic sessions → one file, all section headers
  present, no text fields leak, size under the target.

Expected size (unverified estimate): model-call and caption rows are about 80–120 bytes each; a 5-minute session has a
few hundred of each, so roughly 30–60 KB per session.

### Home screen test buttons
Saving stays manual (no auto-save on broadcast stop). Add to Home, in `toolsSection` as `HomeToolTile`s, visible when
"Save diagnostic sessions" is on:
- **Save run**: calls `diag.persistSession()` (same as Diagnostics → Save now). Shows the session's mode and a
  checkmark when saved; shows why if it was not saved (private session, already saving).
- **Clear test memory**: empties `processMemory.temporary` (Temporary Memory is process-owned and today survives mode
  switches, diagnostics reset and app switching; only quitting the app clears it). Disabled while a broadcast is running.
  Asks for confirmation. Never touches saved memory or `processMemory.normal`.
- **Export test report**: the same action as in Diagnostics, so the whole test can be done from Home.

Test routine per mode: run → stop broadcast → **Save run** → **Clear test memory** → switch mode → run.
After the last mode: **Export test report** → attach the one file to a chat.

### Where it goes
Attach the one report file to a chat. After the analysis, save only the short findings to the Project
(`claude/diagnostics-analysis-*.md`), not the raw report, because Project files can be loaded into every chat.

## 10. Home: translation mode switch

Today the mode picker is only in Settings → Translation (`TranslationSettings` in `SettingsCategories.swift`), several
taps away, and a change made during a broadcast only applies after the broadcast stops.

Add to Home (Live tab), near the start button:
- A three-way segmented control: **Legacy · Hybrid · Low Latency**, bound to the same `@AppStorage("translationSystem")`
  key, calling `engine.translationSystemChanged()` on change, exactly like the Settings picker. No new key, no migration.
- Under it, one line with the active system, and, when `engine.pendingTranslationSystem` differs from
  `engine.activeTranslationSystem`, "Applies when the broadcast stops".
- Keep the Settings picker; both edit the same key.

With §9 the test routine fits on one screen: run → stop → Save run → Clear test memory → tap the next mode → run.
